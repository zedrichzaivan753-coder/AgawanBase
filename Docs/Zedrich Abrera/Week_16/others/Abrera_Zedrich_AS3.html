2. Method, and the one time the method failed

The module asks for one change at a time so its effect can be examined. One change was made, so this was easy to honour:

  1. Measure a baseline (perf_baseline2_run{1,2,3}).
  2. Make one change, rebuild with byte-identical settings, re-measure (perf_fix1_run{1,2,3}).
  3. Fail the comparison. Those three runs, and six more (fix1b, fix1c), degraded monotonically from 0.68 to 2.07 ms mean while the baseline sat at 0.62-0.63 ms with a 0.01 ms spread. GPU time drifted the same way (0.49 -> 0.60 -> 0.71 ms). The host was carrying an unrelated Client-Win64-Shipping process holding 5.4 GB. A texture downsample cannot triple main-thread time, and the GPU moving with it is what a busy GPU looks like.
  4. Instead of publishing a number from a busy machine, **build the A/B pair and re-measure both on an idle host.** The four textures were returned to their original import settings, the player rebuilt (181.41 MB - exactly the pre-fix artefact size), and then both builds were measured minutes apart: perf_baselclean_run{1,2,3} and perf_fix1clean_run{1,2,3}.

Step 4 is the part worth defending. A contaminated measurement is not a measurement, and the only way to know which of two numbers was contaminated is to take both again under the same conditions.

The change does not move frame time, and this report does not claim that it does. Game.unity does not reference the four textures, so the measured scenario never samples them. The earlier 0.63 -> 0.60 comparison in the contaminated sets was host state, and the A/B pair proves it.

That is the honest result, and it still satisfies the module's completion checkpoint twice over: there is a measurable improvement (-20.0 MB of runtime texture memory, -10.00 MB of shipped data), and there is a technically valid finding that the tested area already meets the target (1.8 % of a 33.3 ms budget, ~50x headroom).

3.3 One result that runs the wrong way

In the same A/B pair the optimised build reports 89 textures / 45.3 MB against the pre-fix build's 82 / 44.8 MB, consistently across all three runs of each set. The four maps cannot explain it - Game.unity does not load them - and this harness does not enumerate textures, so the cause is unknown. It is printed here rather than quietly dropped, because a before/after table that only moves in the author's favour is not evidence. The fix's memory benefit is claimed where the textures live: the import settings, the runtime size measured directly, and the build artefact.

No script changed for the optimisation. The evidence named an import setting, so the fix is an import setting; a code change would have had to be invented to look like work.

4.2 The defect the regression gate found, and the fix

Assets/Scripts/Core/PlayerProfile.cs, Load(): added lastError = "" plus a comment. Load() reset the state and the loaded flag but never cleared the last error, and the missing-file branch returns before anything sets one - so a load could inherit the previous load's rejection reason. It surfaced as an order-dependent EditMode failure (section 6.2) and was reachable in the game through any load-see-a-rejection-load-again path. No test was edited.

5. Trade-offs

5.1 Accepted

Visual resolution of four prop textures, from 2048 to 512. This is a real quality reduction and it is justified three ways: the objects are a bench, a tricycle, a stall and a crate stack, seen from a third-person camera a few metres away on a phone screen; both the Windows and Android builds use Mobile_RPAsset at render scale 0.8, so the final on-screen resolution is already below 1080p; and the alternative - leaving 21.3 MB of texture memory on four minor props - costs a mid-range phone something real (resident memory, load time, eviction pressure) to protect detail nobody can resolve at that distance. Mipmaps stay on and compression stays Compressed, so no new aliasing was introduced.

5.2 Rejected, with reasons

Candidate Why it was rejected
HDR off / render scale below 0.8 Both are visible quality losses across the whole screen, taken to buy frame time the game already has (1.8 % of budget). The module requires a trade-off to be justified; this one buys nothing.
Disabling shadows Already disabled on the Mobile path.
Object pooling / allocation work ~320 B/frame is ~10 KB/s at 30 fps. A refactor of gameplay code covered by 16 regression cases, to remove GC pressure that does not exist.
Draw-call reduction Already 17 render events with static and SRP batching; what remains are the passes that must happen.
Chasing the rare 10 ms frames Not reproducible inside a 60 s window, so a change could not be shown to have fixed it.
A second optimisation for the report's sake Would have meant inventing a bottleneck. The analysis found one, and one is what it fixed.

6.1 Where the suites live

The play-mode suite is Assets/Editor/QualityRun.cs (menu Tools > Week15 > Run Quality Scenarios), not an NUnit assembly - it enters play mode and drives a real 4v4 match through the same public methods the rules use, recording one TSV row per case. It was run with the label week16_regression; the harness writes to Week_15/Evidence/test_logs_week16_regression/ and the files in this week's evidence folder are unedited copies. The 24 accessibility items are checks the audit cannot perform from a scene; they are recorded as not-measurable, never as passes.

6.2 The gate caught something, and that is the point of a gate

The first EditMode run was 16/17: PlayerProfileTests.MissingSave_LoadsDefaultProfile_WithoutAnError failed, reporting LastError = "the file is empty" when a save file did not exist at all. It was proved order-dependent before anything was touched - the same test alone passes - and traced to Load() not clearing lastError while NUnit runs the fixture in name order, so EmptySave_LoadsDefaultProfile always handed it a stale message. Fixed in the product (4.2), re-run 17/17, with every file under Assets/Tests/EditMode/ still carrying its Week 15 timestamp as proof that no test was modified.

It was not a Week 16 regression - the optimisation touched four texture import settings - but it would have shipped, and the gate is the reason it did not.

6.3 What the gate does not cover

The suites test functional rules, not performance; nothing in them is quoted as a timing measurement. They ran against the editor's scene tree, not against the shipped .exe. And they are the Week 15 suites unchanged, so they prove the optimisation broke nothing known - they cannot prove an optimised path is correct if that path has no case.

7. Evaluation

Does the build meet the target? Yes, on the measured environment: 0.60 ms of main-thread work and 0.48 ms of GPU time per frame against a 33.3 ms budget, with p95 at 0.88 ms. The margin is roughly 50x.

Was the optimisation worth making? Yes, but for memory and storage, not frame time: -20.0 MB of runtime texture memory and -10.00 MB of shipped data, at no visible cost. On a phone, where Mobile_RPAsset at render scale 0.8 is already the shipping path and memory is the scarce resource, that is the number that matters.

What did the week actually teach? That the honest outcome of a profiling week can be "the thing you expected to be slow was already fast". The value is in knowing it with numbers, in having a harness that writes its own conditions into every file so a result can be checked later, and in having caught two instrument defects and one real product defect along the way.

What still limits this report? Section 9.

9. Limitations, stated plainly

  • No phone was measured. Every timing number is from a Windows standalone development build on a GTX 1070. The APK is built and verified (IL2CPP, ARM64, classes.dex at root) but not profiled; no Android device was available this week. Anything said about phone frame time would be an inference.
  • One scene. Game.unity only. The other two maps and their props never load in this scenario, which is exactly how the section 7.2 error in SA6 happened.
  • The APK's size delta is not measured. The -10.00 MB figure is for the Windows artefact, where both builds were made by the same tool with the same settings. The APK was not rebuilt in a pre-fix variant, so no APK delta is claimed.
  • The texture-memory delta was measured in the editor (Profiler.GetRuntimeMemorySizeLong), on the same API both times, because the player's own capture cannot see textures its scene never loads.
  • Host state is a measured hazard: it moved this game's main thread by 3x within one evening. Every comparison in this report is therefore same-host, same-sitting, A/B, and anything else in raw_csv/ is labelled as contaminated.
  • Loading time, battery use and thermal behaviour are not measured.
