 2. THE FAILURE THIS GATE FOUND, AND WHAT WAS DONE ABOUT IT
=====================================================================

The FIRST run of the gate was NOT 17/17. It was 16 passed / 1 failed:

  2026-11-18 15:51 UTC (23:51 local)
  PlayerProfileTests.MissingSave_LoadsDefaultProfile_WithoutAnError  FAILED
  message: "  a missing save is normal on a first run, not an error
             Expected: <empty>
             But was:  \"the file is empty\""

That is not a Week 16 regression - the optimisation change touched four texture import
settings and nothing else. It is an ORDER-DEPENDENT failure in the product code, and it
was proved to be one before anything was changed:

  isolation run, 2026-11-18 15:51 UTC: the same test, run alone -> PASSED (1/1, 0.31 s).
  full-suite run:                      the same test, run after its siblings -> FAILED.

Cause, read off the source rather than guessed:

  Assets/Scripts/Core/PlayerProfile.cs, Load():
    loaded = false;
    state  = new ProfileState();
    ...
    if (!File.Exists(path)) { loaded = true; ...; return; }   // <- no lastError reset

  Load() reset the state and the loaded flag but never cleared lastError. The missing-file
  branch returns before anything writes an error, so LastError still held the reason the
  PREVIOUS load rejected a file. NUnit runs the fixture in name order, so
  EmptySave_LoadsDefaultProfile ("the file is empty", PlayerProfile.cs:494) always ran
  immediately before it and handed it a stale message. In isolation there is no previous
  load, so the assertion held.

Fix applied - PRODUCT code, one line plus a comment, at PlayerProfile.cs Load():

    // A load reports only its OWN outcome. Clearing this first matters because the
    // missing-file branch returns before anything sets an error: without this line a first
    // run would inherit the reason a previous load rejected a file, and LastError would say
    // "the file is empty" about a file that does not exist. (Week 16 regression gate found
    // this as an order-dependent EditMode failure; the test was left untouched.)
    lastError = "";

No test file was touched to make this pass. Proof, not assertion:

  Every one of those timestamps is from the Week 15 session. The gate and the fix ran at
  23:51-23:54 local, and no test file carries a timestamp from that window.

Why it matters for the build rather than only for the test: the stale value was reachable
in the game too. Anything that loads, sees a rejected save, then loads again through the
SetDataDirectory seam (PT5 checks, the reset path) could read an error that described a
different file. The profile now reports only its own load outcome.
