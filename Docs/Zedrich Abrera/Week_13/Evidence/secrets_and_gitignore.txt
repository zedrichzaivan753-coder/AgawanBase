1. THE SCAN
-----------
Run from the project root, against every hand-written script, the package manifest and the
project settings (the three places a credential can realistically hide in a Unity project):

  findstr /s /i /n /r
      /c:"api[_-]key" /c:"secret" /c:"password" /c:"access[_-]token"
      /c:"private[_-]key" /c:"bearer " /c:"firebase" /c:"playfab" /c:"client[_-]secret"
      Assets\Scripts\*.cs  Assets\Editor\*.cs  Packages\manifest.json  ProjectSettings\*.asset

Output:

  ---SCAN-START---
  NO_MATCHES_FOUND

No API key, no token, no password, no private key, no bearer header, and no reference to a
cloud backend appears anywhere in the source, the package manifest or the project settings.

2. NO CLOUD PACKAGE IS INSTALLED
--------------------------------
  findstr /i "firebase playfab unity.services" Packages\manifest.json
    -> NO_MATCHES_FOUND

There is no Firebase, no PlayFab, and no Unity Gaming Services package in this project. That
is the build-level reason the identity model is a local profile (SA5 section 6): there is no
service to hold a key for, so there is no key to leak.

3. NO NETWORKING CODE, NO FORCED NETWORK PERMISSION
---------------------------------------------------
  grep for UnityWebRequest | HttpClient | System.Net | Socket across Assets/Scripts/*.cs
    -> No matches found.

  ProjectSettings/ProjectSettings.asset
    -> no "forceInternetPermission" key at all (i.e. the Player Setting is at its default: off)

  Assets/Plugins/Android/AndroidManifest.xml
    -> does not exist (NO_CUSTOM_ANDROID_MANIFEST)

So the build references no networking API, keeps no custom Android manifest, and does not ask
Unity to force the INTERNET permission. The precise claim this evidence supports is: the game
contains no networking code and forces no network permission. It is not a claim about what the
Android toolchain may or may not merge in for a future build - that would be checked with
aapt on a real APK, which was not done.

4. THE ONLY SECRET-LIKE VALUE, AND WHY IT IS NOT IN THE REPOSITORY
------------------------------------------------------------------
The signature salt is the one value in this design that behaves like a key. It is:

  - 16 bytes from System.Security.Cryptography.RandomNumberGenerator
  - generated on the device, on first save
  - stored in PlayerPrefs under the key "profile.salt", base64-encoded
  - never written to source, never written to the save file, never committed

There is no constant anywhere in Assets/ that could be extracted from the APK and reused
against every install, which is what a hard-coded key would have allowed. This is why the scan
above comes back empty and why the salt does not appear in it.

Honest limit, repeated here because it is the point of the exercise: the salt sits on the same
device as the file it signs. It raises the effort of forging a save; it does not prevent it.
PT5 sections 4 and 5 and check L15 say the same thing.

5. IGNORE RULES THAT KEEP ARTEFACTS OUT OF THE REPOSITORY
---------------------------------------------------------
.gitignore, lines 81-89 ("Builds"):

  # Builds
  *.apk
  *.aab
  *.unitypackage
  *.unitypackage.meta
  *.app

  # Crashlytics generated file
  crashlytics-build.properties

Effect on this submission: the APK at
Docs/Zedrich Abrera/Week_13/Abrera_Zedrich_PT5.apk
(40,876,464 bytes) is NOT tracked by Git. It is an artefact that can be rebuilt from tracked
source, it changes byte-for-byte on every build, and it is 39 MB. The folder it sits in is the
submission folder, not a version-control folder, and the build_and_commit.txt file records the
exact commit and settings that produced it.

Unity's generated folders are excluded by the same file (Library/, Temp/, Logs/, obj/,
UserSettings/, *.csproj, *.sln), so the repository contains source, settings, scenes and assets
only - nothing that a fresh clone would have to download or that would carry machine-specific
state.

6. WHAT IS *NOT* CLAIMED
------------------------
- This is a static scan of this repository on this date. It proves the absence of credentials
  now; it does not prevent one being added in a future commit.
- No secret-scanning service or pre-commit hook is configured in this project. The check above
  is a manual step recorded as evidence, not automation.
- The save file itself is not encrypted and does not contain a credential; it contains a
  player-typed name and match results only (SA5 section 4, the data inventory).
