1. What was built

The game now remembers the player. A profile screen reachable from the title screen holds a display name, a win/loss/draw record with the current and best win streak, and a local best-times board of the five fastest victories. The record is stored in a signed JSON file in the app's own sandbox, and it survives closing and reopening the game.

2. Where the player meets it

  1. The title screen gains a PROFILE button under START.
  2. Pressing it puts GameManager into GameState.Profile, which hides every other panel and shows Panel_Profile (backdrop alpha 0.94).
  3. The player types a name (the field itself refuses past 16 characters), presses SAVE, and the status line confirms. BACK returns to the title.
  4. Playing a match to an end banks exactly one entry: win, loss or draw, with the ending type, the match clock in seconds, the map, the team size and the difficulty.
  5. Reopening PROFILE shows the updated record and, for a victory, a line on the fastest-victory board.
  6. RESET PROFILE is deliberately two presses within 4 seconds; the first press renames the button to PRESS AGAIN and says what will be lost.

Each step is photographed in Evidence/ (E1 to E4, listed in section 8).

3. The save file

Location

Platform Path
Android /data/data/com.zedrich.agawanbase/files/AgawanBase/profile.json (i.e. Application.persistentDataPath/AgawanBase/profile.json)
Windows editor C:/Users/<user>/AppData/LocalLow/<company>/AgawanBase v0_2/AgawanBase/profile.json

The folder is the app's private sandbox. No other app on the phone can read it, and uninstalling the game deletes it. Nothing is written anywhere else.

Format

One UTF-8 JSON envelope: an int schema for future migrations, a string sig holding the signature, and the payload that the signature covers.

{
    "schema": 1,
    "sig": "6b1f0d5a91c7e4a2b8d3f6071c2e9a4b5d6c7e8f90a1b2c3d4e5f60718293a4b",
    "payload": {
        "schema": 1,
        "playerName": "Zedrich Abrera",
        "wins": 2,
        "losses": 1,
        "draws": 0,
        "currentStreak": 1,
        "bestStreak": 2,
        "lastMatchId": 3,
        "lastPlayedUtc": "2026-11-18T11:42:07Z",
        "recent": [
            {
                "matchId": 3,
                "result": "WIN",
                "outcome": "FLAG_CARRIED_HOME",
                "seconds": 47.3,
                "mapId": "palengke",
                "teamSize": 2,
                "difficulty": "NORMAL",
                "whenUtc": "2026-11-18T11:42:07Z"
            }
        ]
    }
}
Field Type Rule enforced by PlayerProfile
schema int Refused and quarantined if it is newer than SchemaVersion (1)
sig string Lowercase hex SHA-256; compared with StringComparison.Ordinal
payload.playerName string Trimmed, control characters stripped, runs of spaces collapsed, capped at 16, blank becomes PLAYER
payload.wins / losses / draws int Floored at 0 after the signature passes
payload.currentStreak int Floored at 0; reset to 0 by a loss, kept by a draw
payload.bestStreak int Raised to at least currentStreak, so an edited save cannot show a streak better than the record
payload.lastMatchId int Floored at 0. RecordMatch refuses any id at or below it, which is what makes a double-bank impossible
payload.recent list Null entries removed; trimmed to 20 newest

*.apk is listed in .gitignore, so the build under Week_13/ is deliberately outside version control. The source that produced it is not.

4. Integrity design

Six decisions, in the order they protect the file.

4.1 The save is signed, and the signature is over the canonical payload. On write, the payload is serialised with JsonUtility.ToJson(state) and that exact string is signed. On read, the file is parsed and the payload is re-serialised with the same call before the signature is recomputed. Signing the raw text of the file instead would have made the check depend on whitespace and key order, so a cosmetic difference would have looked like tampering. The canonical form is the contract.

4.2 The key is per install and never shipped. ComputeSignature prepends a 16-byte salt generated by RandomNumberGenerator on first save and kept in PlayerPrefs["profile.salt"] as base64. There is no constant in the source, so a compile of the game does not contain the key, and two installs sign differently.

4.3 The write is atomic. The JSON goes to profile.json.tmp, the old file is deleted, and the temp file is moved into place. A process killed mid-write leaves a .tmp file behind, never a half-written profile.json where a complete one used to be.

4.4 A rejected file is quarantined, not destroyed. When parsing or the signature check fails, the file is moved to profile.rejected.json and a fresh default profile starts. A player's only copy is never overwritten by a game that did not understand it, and if this ever happens for real, the rejected file is the evidence.

4.5 Numbers are clamped even when the signature passes. A correctly signed file is still a file, and a correctly signed file is what an attacker with the salt produces. So after the signature passes, negatives are floored, bestStreak is raised to at least currentStreak, the name is re-sanitised and the recent list is cleaned. Conservative clamping means an edited save degrades to something plausible instead of something impossible.

4.6 There is exactly one gate, and it is a match id. RecordMatch returns early when matchId <= lastMatchId. GameManager also keeps its own recordedMatchId field, so a duplicated end-of-match callback cannot bank a match twice even before it reaches the store. Two independent guards for the same failure, because an inflated record is the failure mode that actually matters to a player.

Rejected alternative: encrypting the file. There is no key the attacker does not have, so encryption would add code, a decryption failure path, and the false impression of a guarantee, without changing who can produce a valid file. It is not in the build and section 5 says so on the record.

5. What the signature does not do (the honest limit)

The save is tamper-evident, not tamper-proof.

  • It is not encrypted. Anyone who can read the file can read the name and the record.
  • The salt lives on the same device as the file. A determined local attacker can extract it and re-sign an edited save, and the game will accept it.
  • There is no server, no account and no online leaderboard, so there is nothing to verify the record against. For an offline single-player playground game this is the true ceiling, and it is stated rather than hidden.

This is recorded in the check log as L15 KNOWN LIMIT rather than passed off as a pass, and it is repeated in README.md under known limitations.

TOTAL: 15 passed, 0 failed

Two details worth stating, because they are what the checks are actually worth:

  • L12 plants a save whose numbers are impossible but whose signature is correct. It passes the signature gate and is then clamped. This proves that the signature is not being used as the only defence.
  • L14 does not merely fail to crash: PlayerProfile.LastError carries the operating system's own message, and ProfileUI prints it, so a real player would see "Could not save." followed by the reason rather than a silent no-op.
