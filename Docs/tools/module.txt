Introduction
This laboratory module guides each student through the final six weeks of an individual mobile game development project. Every student will design, implement, test, optimize, document, and defend an original game based on one approved theme. The laboratory emphasizes independent technical decision-making, measurable evidence, responsible use of services and data, and a complete playable build rather than a concept-only submission.
The selected theme must affect the game mechanics, player decisions, goals, content, and feedback. A generic game with only a themed title, background, or set of images will not satisfy the requirement. All source code, assets, documentation, test evidence, repository history, and demonstrations must represent the individual student's work, with third-party and AI-assisted materials properly acknowledged.
Project Overview
• This is an individual mobile game development project.
• Each student must select one approved theme and create one original game.
• The selected theme must influence the gameplay, goals, decisions, feedback, and player experience.
• All weekly outputs must be produced from the same individual game project.
• Each student must maintain an individual Git repository with meaningful commits.
• The final output must be installable, playable, documented, tested, optimized, and independently defended.

Learning Objectives
Upon completing this laboratory module, the student should be able to:
• Implement secure player data handling, authentication or profile management, and responsible AI-assisted development practices appropriate to the game.
• Plan and conduct an ethical usability and accessibility evaluation using observable player tasks and documented evidence.
• Design and execute functional, compatibility, regression, and acceptance tests and use the results to correct defects.
• Profile CPU, GPU, memory, rendering, loading, and responsiveness and verify measurable improvements after optimization.
• Integrate gameplay, user interface, services, security, testing, optimization, deployment, and documentation into a stable release candidate.
• Demonstrate and independently defend the completed mobile game using technical evidence and reflective evaluation.

Minimum Acceptable Game Requirements
• Title or start screen and clear instructions or tutorial.
• A complete core gameplay loop with an understandable player goal.
• Mobile-compatible player input and immediate visual, audio, or haptic feedback where appropriate.
• Win, loss, completion, scoring, or progression conditions appropriate to the game.
• Pause or settings function and a restart, retry, or reset function.
• Credits and acknowledgements for third-party and AI-assisted resources.
• A working player-data or approved service component.
• Error handling and a stable installable mobile build.
Technical Glossary
Build: A packaged version of the game that can be installed or run for testing.
Release candidate: A complete version intended for final testing and demonstration, with no unfinished experimental features.
Repository: The student's individual version-controlled project containing source files and development history.
Commit ID: The unique identifier of a saved repository revision used to verify the submitted version.
Core gameplay loop: The actions the player repeatedly performs to progress in the game.
Regression testing: Retesting existing features after a change to confirm that previously working behavior remains correct.
Traceability matrix: A table linking requirements or features to the test cases that verify them.
Baseline: The controlled measurement recorded before an optimization is applied.
Profiler: A tool that measures CPU, GPU, memory, rendering, loading, and related performance behavior.
Bottleneck: A verified component or process that limits performance or responsiveness.
Evidence portfolio: An organized collection of diagrams, tests, screenshots, recordings, commits, profiler captures, and evaluation findings.

Weekly Self-Assessment and Reflection Guide
A Self-Assessment and Reflection PDF is required every week from Week 13 through Week 18. Its purpose is to document the student's authentic development experience, not to repeat the module instructions or summarize a topic. The writing must explain what the student personally attempted, observed, changed, learned, and still needs to improve.
Recommended Written Structure
• Project identification: game title, theme, week, build version, repository branch or tag, and commit ID.
• Work completed: describe the specific feature, analysis, test, optimization, or documentation completed during the week.
• Evidence from experience: identify the exact file, scene, script, test case, defect, commit, measurement, or player observation that supports the reflection.
• Challenge encountered: explain one real technical or design difficulty, how it was diagnosed, and what was attempted.
• Decision and result: explain one decision made because of evidence and describe its effect on the game.
• Self-assessment: identify what was done well and what remains incomplete or weak.
• Next action: state one specific improvement for the following week and explain its priority.
• Authenticity declaration and disclosure of any assistance received.
PDF Preparation and Authenticity Rules
• Write the reflection in the student's own words before exporting it to PDF.
• Use first-person statements such as I implemented, I tested, I observed, I changed, and I learned when they accurately describe the student's experience.
• Do not submit a generic topic summary, copied laboratory instructions, or a list of activities without explanation.
• Repository commits, build versions, screenshots, tests, defects, and measurements may be checked against the reflection.
• AI may assist with grammar only when disclosed; it must not invent experiences, decisions, evidence, results, or personal reflection.
• Export the final document as PDF and reopen the PDF to verify readability before submission.

Week 13 Laboratory
Secure Player Data and Responsible Development
Laboratory Purpose
The student will identify the data used by the game, implement an appropriate player-profile or authentication flow, protect sensitive configuration values, and document responsible use of AI and third-party resources. The security requirement must be proportionate to the game: an offline game may use a local profile and protected save design, while an online game may require authentication, authorization, and cloud data rules.
Guided Laboratory Procedure
1. Create a data inventory identifying every player, device, gameplay, analytics, and service-related data item collected, generated, stored, or transmitted by the game.
2. Draw a concise data-flow diagram showing where each data item originates, where it is stored, who or what can access it, and when it is deleted or reset.
3. Choose and justify the required identity model: no account, local profile, anonymous authentication, email authentication, or another instructor-approved approach.
4. Implement the player-profile or authentication flow. Validate inputs, provide useful error messages, and prevent unauthorized access to another player's records.
5. Remove secrets from source code. Store keys, configuration values, and service credentials using an appropriate configuration method, and verify that sensitive files are excluded from the repository.
6. Test successful access, invalid input, failed network access where applicable, sign-out or profile reset, and recovery from interrupted service communication.
7. Complete a responsible-development record listing AI tools, external assets, code references, generated content, licenses, modifications, and verification performed by the student.
8. Commit the working security and player-data changes with a meaningful commit message and record the commit identifier.

7. Compare baseline and optimized results, calculate meaningful differences, and note trade-offs in quality, maintainability, battery use, storage, or gameplay.
8. Retain only changes that produce a defensible benefit without breaking required behavior, then rerun the relevant regression tests.

Laboratory Evaluation Criteria
• Theme and gameplay coherence: The selected theme is meaningfully expressed through mechanics, goals, decisions, feedback, and player experience.
• Technical implementation: The game is functional, appropriately structured, maintainable, and demonstrates individual programming and integration work.
• Security and responsible development: Player data, credentials, services, third-party resources, and AI assistance are handled responsibly and transparently.
• Usability and accessibility: The interface and controls are evaluated with real player evidence, and significant findings are addressed.
• Testing and reliability: Requirements are traceable to tests; defects are reproducible, prioritized, corrected, and regression-tested.
• Performance optimization: Profiling is controlled and repeatable; improvements and trade-offs are supported by measurements.
• Documentation and repository evidence: Documentation, commits, credits, licenses, diagrams, and evidence are complete and verifiable.
• Demonstration and individual defense: The student operates the final build confidently and independently explains the code, architecture, decisions, evidence, and limitations.
